# Rust 1.99.1: official LLVM profile audit and matched revalidation

## Qualified result: 12.93% less offline compilation wall time

Replacing only the LLVM profile in otherwise matched Rust **1.99.1** rebuilds
reduced the original five-command IronRDP workload from **631.608 to 549.949
seconds**: **81.659 seconds / 12.93% less wall time**. Process-tree CPU fell from
**2451.901 to 2116.984 seconds**, a **13.66% reduction**. Both complete
distributions passed the unmodified upstream extracted-distribution tests.

This revalidates the direction and approximate size of the earlier
[Rust 1.94.1 profile-only result](X64-PROFILE-ONLY.md), which saved 13.73% wall
time. It does not establish a statistically significant difference between
Rust versions, nor compare either rebuild directly with an untouched shipping
compiler binary.

| Offline native component | Official-profile wall (s) | Repaired-profile wall (s) | Wall reduction |
|---|---:|---:|---:|
| xtask bootstrap | 2.966 | 2.614 | 11.89% |
| Workspace test compilation | 489.911 | 426.643 | 12.91% |
| Native TLS test compilation | 11.132 | 9.966 | 10.47% |
| Gateway native TLS test compilation | 64.158 | 55.915 | 12.85% |
| Gateway smartcard test compilation | 63.441 | 54.811 | 13.60% |
| **Five-command total** | **631.608** | **549.949** | **12.93%** |

There are three measured rounds per compiler after one excluded warmup,
on one dedicated host with four replay workers. All three paired rounds
improved: **13.65%, 13.79%, 11.34%**. Their **11.34-13.79%** range is descriptive,
not a confidence interval. All 30 measured Cargo commands and eight untimed
original correctness commands passed. Setup, downloads, correctness tests and
uploads are outside the reported native compilation times.

## Official profile audit: complete

The official Windows x64 Rust **1.99.1** reproducibility bundle has no LLVM profile
records matching either backend group:

| Official release | X86TargetLowering functions / active | InstCombine functions / active |
|---|---:|---:|
| 1.94.1 | 0 / 0 | 6 / 0 |
| **1.99.1** | **0 / 0** | **0 / 0** |

The archives were checked against their published SHA-256 files. The profile
bundle and the matching LLVM tools both identify Rust source
`58cf8f9c35b355199727627d07ae34a4e2846d67`. The reader reports
`23.1.1-rust-1.99.1-stable`. This establishes a coverage gap in these exact
substring queries; it does not establish that all official PGO is ineffective.

The published profile contains 38,612 total functions. Its SHA-256 is
`0967c426f74d7341438ed98b2b9b01db8ec8146704ee4d34614663b354cfe175`.
The [machine-readable audit](X64-PGO-1991-AUDIT.json) includes archive URLs,
checksums, all supplied profile identities and the reader identity.

The newly trained profile restores coverage in both groups. The final-build
profile files were independently re-read with the matching official LLVM reader:

| Backend query | Official functions / active | Repaired functions / active |
|---|---:|---:|
| X86TargetLowering | 0 / 0 | **273 / 176** |
| InstCombine | 0 / 0 | **971 / 624** |

The repaired LLVM profile SHA-256 is
`3fb57e2e25be6f1c518c2fa7b6ca29308eadf77484bdb0555a1b2c941bfc4ee7`.
It was frozen before either comparison build. Both builds retained the same
official rustc/Cargo and rustdoc profiles, Microsoft link/lib, source and LTO
settings; IronRDP was not in the training workload.

Reproduce on Windows with Python 3.13:

```powershell
python ci-benchmark\audit_official_profiles.py 1.99.1 C:\audit-rust-1991
```

## Execution history and matched protocol

The replacement workflow completed successfully at **19:19 UK time on
22 October 2026**, about **6h49m** after dispatch. Training, both full
distribution qualifications and the replay passed in the original attempt.

Initial workflow:
[39769031282](https://github.com/marcpems/IronRDP-ci-benchmark/actions/runs/39769031282),
using harness commit `086808be2232e49292676ad85de24aad9c5a5d45`.
Runner and ReFS storage checks passed, but the source-integrity guard stopped
the job before training. The runner's automatic post-checkout hook had inserted
five ASan test exclusions into LLVM's release batch script. A read-only
[diagnostic](https://github.com/marcpems/IronRDP-ci-benchmark/actions/runs/39770800349)
preserved the original and modified bytes. No measurements from that attempt
are accepted.

The replacement uses a new source directory and an empty, experiment-owned
Git hook directory through process-local configuration. The machine's global
hook configuration and the rejected checkout are left unchanged.
Replacement run:
[39771158637](https://github.com/marcpems/IronRDP-ci-benchmark/actions/runs/39771158637),
harness `d37b0ed6e6ebdeb17d5bdaaa12e6e5166bf09d95`.

The [preregistered protocol](x64-profile-1991-protocol.json) uses:

- Fresh training on pinned Rust 1.99.1, LLVM 23.1.1 and its rustc-perf submodule,
  with the static-LLVM relink repair and the unchanged upstream training code.
  IronRDP is not a training workload.
- Upstream clang-cl 20.1.3 and Microsoft link/lib throughout. No added ThinLTO.
- Two clean complete distributions at the same source path. Both use the same
  official rustc profile for rustc/Cargo and the same official rustdoc profile.
  Only the final LLVM profile differs.
- A repaired profile hash frozen after training and before either comparison
  build; both queried LLVM backend groups must have active functions.
- Unmodified upstream extracted-distribution correctness tests for each compiler.
- The original pinned five-command offline IronRDP native workload, using the
  same official 1.99.1 Cargo/std, four workers, one excluded warmup and three
  measured rounds per compiler with alternating order.

The single available dedicated x64 runner uses the previously qualified D: ReFS
NVMe disk and 16 workers for compiler production. Correctness TEMP/TMP remains
on C: NTFS. Only compact compiler inputs are downloaded for replay; complete
distributions and evidence are preserved separately before guarded cleanup.

Training, fixed-profile distribution production, qualification and consumer
compilation are separate endpoints. This is **not** a matched fresh-training
release-CI cost comparison, nor an untouched shipping-binary comparison. Any
paired-round range is descriptive, not a multi-runner confidence interval.

## Compiler production and experiment wall time

| Endpoint | Official profile | Repaired profile |
|---|---:|---:|
| Fixed-profile full distribution production | 4336.817 s (72m17s) | 4218.885 s (70m19s) |
| Separate build-helper and distribution qualification | 583.523 s | 580.608 s |
| Whole distribution job, including setup/uploads/cleanup | 112m42s | 113m20s |

Fixed-profile production was **117.932 seconds / 2.72% shorter** with the repaired
profile in this one ordered build pair. **This is not the release-cost impact of
the training fix:** these production timers exclude profile generation. The
whole-job ordering also differs from the production-only ordering because
setup and artifact transfer have separate costs.

Standalone repaired training took **4833.266 seconds (80m33s)** including helper
preparation, training and profile processing. Its nested upstream timers report
**3339.65 seconds** for Rust-side PGO and **1273.04 seconds** for LLVM PGO.
There is no corresponding fresh upstream-training control in this experiment,
so neither the marginal training cost nor the official release-job percentage
for PR #164707 can be derived from these numbers.

| Serial experiment job | Whole-job wall time |
|---|---:|
| Training and profile validation | 1h34m52s |
| Official-profile build and qualification | 1h52m42s |
| Repaired-profile build and qualification | 1h53m20s |
| Eight-block replay, including warmups and setup | 1h27m51s |

Within the replay job, the measured commands account for **3544.670 seconds**,
excluded warmup commands **1178.739 seconds**, original correctness checks
**57.293 seconds**, other benchmark-step activities **167.298 seconds**, and
outside-step setup/download/upload activities **323 seconds**. These add to
the **5271-second experimental replay job**, not a single-toolchain CI run.

Build telemetry retained at least **1772 GiB free on D:** and **6239 MiB
available RAM** across both production/qualification runs. No invalid
performance-counter samples were accepted.
